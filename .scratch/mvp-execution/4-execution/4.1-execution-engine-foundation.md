## Problem Statement

The execution of a workflow requires a foundation that can receive an execution request, fetch the workflow definition, initialize a running state, traverse the nodes sequentially, and log the final outcome. We need this foundational engine before we can implement specific node functionalities.

## Solution

Build the core Execution Engine service and the `POST /api/executions` endpoint. This engine will focus solely on graph traversal (following edges from start to finish) and creating the database records for `executions` and `execution_node_logs`.

## User Stories

1. As a user, I want to click a "Run" button to hit an API endpoint that starts the execution process for my workflow.
2. As a system, I want to record the start, finish, and overall status of the execution in the database so the user can review it later.

## Implementation Decisions

- **API Endpoint**: `POST /api/executions` accepting a `workflow_version_id`.
- **Engine Logic**:
  - Load the workflow definition from `workflow_versions`.
  - Validate that a `trigger.manual` node exists and start traversal from there.
  - Traverse the graph by following `edges`.
  - For each node visited, create an `execution_node_logs` record with `status=SUCCESS` and mock input/output data (since the actual handlers aren't built yet).
  - Create the parent `executions` record.
- **Synchronous Execution**: The HTTP request will block until the traversal is complete and return the generated execution record.

## Testing Decisions

- **Unit Tests**: Test the graph traversal algorithm with a sample definition JSON to ensure it visits nodes in the correct sequence.
- **Integration Tests**: Verify that calling the API creates the correct `executions` and `execution_node_logs` rows with dummy data.

## Out of Scope

- Executing the actual logic for integrations (Google Sheets, Gmail).
- Handling conditional branching (e.g., if/else paths).
