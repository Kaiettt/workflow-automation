## Problem Statement

A published workflow version has no runner. The MVP starts a **manual** run from an HTTP endpoint, loads that version’s definition, walks the linear graph from `definition.edges` in array order, and persists `executions` plus per-node logs.

## Solution

Add an execution Nest module (Clean Architecture + CQRS). Implement `POST /api/executions` and a traversal engine that follows `contracts.md`. Define `INodeExecutor` and one registered class per catalog key (`ManualTriggerExecutor`, `GoogleSheetReadRowsExecutor`, `FilterExecutor`, `GmailSendExecutor`). Their `execute` bodies are stubs: each visited node logs `SUCCESS` with mock input/output.

Read `contracts.md` in this folder before coding. Use `definition.json` as the unit-test graph.

## User Stories

1. As a caller, I POST `workflow_version_id` and receive the finished execution record after the linear walk completes.
2. As a system, I persist start/finish, overall status, and one log row per visited node.

## Implementation Decisions

- **Endpoint**: `POST /api/executions` body `{ "workflow_version_id": string }`. JWT-auth the caller. 404 if the version is missing; 403 if the caller cannot run that workflow; 400 if `edges` is empty or not a single directed chain (see `contracts.md`).
- **Engine**: Load `workflow_versions.definition`. Walk `edges` in array order (`source` → `target`); do not find `trigger.manual` as start and do not invert edges. Resolve each node via the `INodeExecutor` registry (`key → executor`); never `switch` on `data.key`. Create the parent `executions` row (`trigger_type: MANUAL`) and four `execution_node_logs` rows for the fixture graph (mock I/O from stub executors).
- **Registry**: Define `INodeExecutor` in domain. Register four stub classes in 4.1: `ManualTriggerExecutor`, `GoogleSheetReadRowsExecutor`, `FilterExecutor`, `GmailSendExecutor` located in `application/executors/`. Use shared constants from `execution.constants.ts` (e.g. `NodeKeys`, `ExecutionStatus`) instead of magic strings.
- **Synchronous**: The request blocks until traversal ends and returns the execution DTO (id, status, timestamps, node logs). Do not return domain entities from the controller.
- **Module**: New lib under `monolith-backend/libs/` (e.g. `execution`), kebab-case files, command handlers located in `application/commands/start-execution/`.

## Testing Decisions

- Unit: traversal on `definition.json` visits the four instance ids in `edges` array order (trigger → sheet → filter → Gmail in that fixture).
- Unit: a definition whose `edges` array is a different chain visits nodes in that stored order (engine does not rewrite direction or start).
- Integration: POST creates `executions` and `execution_node_logs` with mock payloads; missing version returns 404.

## Out of Scope

- Real Sheet / Filter / Gmail executor bodies (4.2, 4.3).
- Branching, schedule, webhook.
- Frontend pages (4.4).
