## Problem Statement

4.1 walks the graph with stub `INodeExecutor` bodies. `logic.filter` must apply the configured condition to the previous node’s array, and `trigger.manual` must be a real no-op.

## Solution

Keep the `INodeExecutor` contract and registry from `contracts.md`. Replace stub bodies for `ManualTriggerExecutor` and `FilterExecutor`. Sheet and Gmail stay stubs until 4.3.

Read `contracts.md`. Engine from 4.1 looks up the executor by `node.data.key`, parses config/input according to that executor’s models (skip null schemas), calls `execute`, logs real input/output for filter and trigger.

## User Stories

1. As a developer, I add a node type by registering one `INodeExecutor` with its own models and `key`.
2. As a user, filter keeps only items matching `field` / `operator` / `value`.

## Implementation Decisions

- **Interface**: `INodeExecutor.execute` receives parsed `config`, parsed `input` (or `null`), and `credential` (null for filter/trigger). Executors must not load credentials themselves.
- **Registry**: `trigger.manual` → `ManualTriggerExecutor`; `logic.filter` → `FilterExecutor`. Sheet/Gmail keys remain registered stubs from 4.1.
- **Filter**: operators `equals`, `not_equals`, `contains` on an array of objects. Output the matching items. Engine passes previous output as this input.
- **Engine**: replace stub I/O for trigger and filter with real executor results. Sheet/Gmail stubs still allowed until 4.3.

## Testing Decisions

- Unit: `FilterExecutor` for all three operators on a known array (same rows as `spec.md` example).
- Unit: engine with stub sheet output → filter `status equals new` yields only the two `new` rows.

## Out of Scope

- Google Sheets and Gmail API calls.
- Credential decrypt.
