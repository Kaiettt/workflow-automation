## Problem Statement

With the graph traversal engine in place, the system needs a structured way to execute specific node logic. We need an extensible handler pattern for node execution, starting with the core data manipulation nodes (like `logic.filter`) that do not require external API calls.

## Solution

Define a standard interface for `NodeHandler` and implement the execution logic for the `logic.filter` node type. Integrate this handler registry into the Execution Engine so it invokes the correct handler based on the node's `type`.

## User Stories

1. As a developer, I want a standard NodeHandler interface, so that I can easily add new node types to the execution engine in the future.
2. As a user, I want the filter node to correctly filter data based on the condition I configured, so that only the relevant data passes to the next step.

## Implementation Decisions

- **Node Handler Interface**: Create a `NodeHandler` interface (or abstract class) with an `execute(node, inputContext)` method that returns the output data.
- **Handler Registry**: Create a factory/registry that maps `node_key` (e.g., `logic.filter`) to its handler instance.
- **Filter Node Implementation**: Implement `FilterHandler` which takes the node's `data.config` (field, operator, value) and applies it to the incoming array of data.
- **Engine Integration**: Update the Execution Engine (built in 3.1) to look up and invoke the handler, passing the output of the previous node as the input to the current node, and logging the *actual* input/output to `execution_node_logs`.

## Testing Decisions

- **Unit Tests**: Thoroughly unit test `FilterHandler` with various conditions (equals, not_equals, contains) and mock data arrays.

## Out of Scope

- External integrations (Google Sheets, Gmail) which require credential management.
